# 古籍智能阅读器 V0.1 — OMP 1–2 日冲刺工程计划书

> 项目定位：不是“古籍数据库 / Reading OS”，而是一个 **local-first、马上能读、以后可静态部署** 的古籍辅助阅读器。
>
> V0.1 核心目标只有四件事：
>
> 1. **能读**：繁体正文、好看的护眼 WebUI、横排/竖排、目录导航、古注基本显示。
> 2. **能注**：专名线 + 第一层/第二层 AI 注释，全部由科大词元计划 DeepSeek V4.1 Flash 生成并独立复核。
> 3. **能批**：10 色高亮、10 色波浪线、透明度、个人批注，点击式显示。
> 4. **能保存**：个人标记写入 IndexedDB，刷新/重新打开仍存在。
>
> **V0.1 明确不做**：第三层阶段总结/思考题、第四层现代学术研究、地图、时间轴、人物网络、RAG、知识图谱、云同步、账号系统、FastAPI 服务、全站搜索、移动端深度适配、任意重叠高亮、自动同步 Obsidian。
>
> 这些全部留给 V0.2+。V0.1 的成功标准是：你能打开浏览器，舒服地开始读《通鉴纪事本末》，并且真的愿意继续用。

## 0. Coding 模型路由

### 0.1 原则

Coding 层与古文 LLM 层完全分开：

- **Coding Planner**：只规划、分解、制定数据契约和验收条件，不直接大规模改代码。
- **Coding Executor**：主力写代码、跑测试、修 bug。
- **Coding Reviewer**：独立上下文审查计划符合性、bug、测试缺口、数据污染风险，不负责先入为主地替 Executor 辩护。
- **廉价辅助**：repo grep、文档、小修补、commit 信息。

### 0.2 推荐 OpenCode Go 模型

```yaml
plan:    opencode-go/kimi-k3:max
slow:    opencode-go/kimi-k3:max

default: opencode-go/kimi-k2.7-code
task:    opencode-go/kimi-k2.7-code

review:  opencode-go/glm-5.3:high

smol:    opencode-go/deepseek-v4.1-flash
tiny:    opencode-go/deepseek-v4.1-flash
commit:  opencode-go/deepseek-v4.1-flash
```

原因：

- **Kimi K3**：只用来做一次高质量总体计划，以及真正卡死时的慢任务；不拿它承担日常 coding。
- **Kimi K2.7 Code**：专门面向长程软件工程与 agentic coding，作为 V0.1 主执行器。
- **GLM-5.3**：与 Kimi 不同模型家族，单独承担 code review，降低 correlated error。
- **DeepSeek V4.1 Flash**：用于低成本 repo exploration、简单修改、文档与 commit。
- **不要开 continuous advisor**：V0.1 追求快。Reviewer 只在两个 checkpoint 和最终验收时主动调用。

> 如果 `omp models find <name>` 返回的模型 ID 与上面略有不同，以你本机 OpenCode Go runtime discovery 的 selector 为准。

# 1. V0.1 技术架构：故意比上一版更轻

## 1.1 不上 FastAPI

V0.1 不做长期运行的 Python backend。

架构改成：

```text
Wikisource / MediaWiki API
        │
        ▼
Python 离线构建脚本
        │
        ├── corpus JSON
        ├── source-note JSON
        └── AI annotation JSON
                 │
                 ▼
        React + TypeScript + Vite
                 │
                 ├── 阅读
                 ├── 点击注释
                 └── IndexedDB 私人批注
```

好处：

1. 更容易在 1–2 日冲刺里完成。
2. V0.1 本身天然接近 GitHub Pages 静态部署形态。
3. DeepSeek / USTC API key 永远只存在本机 Python 脚本环境，不进入浏览器。
4. UI 与 AI 生成完全解耦：没有 API 时照样读原文。

# 3. 数据层必须先定死的 invariant

这些规则比 UI 更重要。

## 3.1 canonical text 不可被任何派生层修改

目录建议：

```text
data/
  raw/
  canonical/
  source_notes/
  ai_annotations/
  review_reports/

public/
  data/
    catalog.json
    works/
    annotations/

src/
  ...
```

`raw/`：
- MediaWiki API 原始响应或必要的原始 HTML/wikitext。
- 永不覆盖。

`canonical/`：
- 供阅读器显示的原文。
- 只由 source pipeline 产生。
- AI 无权修改。

`source_notes/`：
- 胡三省等古注。
- 永远标记 provenance。

`ai_annotations/`：
- 第一/二层 AI 注释。
- 与 canonical 分离。

`review_reports/`：
- 第二次 DeepSeek reviewer 的审核结果与统计。

个人批注：
- 不写入上述 corpus。
- 只存 IndexedDB。

---

## 3.2 最小数据模型

### Work

```ts
type Work = {
  id: string;
  title: string;
  editionId: string;
  source: {
    provider: "wikisource";
    url: string;
    retrievedAt: string;
  };
  volumes: VolumeRef[];
};
```

### Passage

V0.1 将“段落”设为最小稳定阅读/注释单位。

```ts
type Passage = {
  id: string;
  workId: string;
  volumeId: string;
  order: number;
  text: string;      // 繁体 canonical text
  sourcePage: string;
  revisionId?: string;
};
```

V0.1 中：
- 用户选择范围 **限制在单个 passage 内**。
- 暂不支持跨段高亮。
- 这是为了把 Selection → canonical offset 做可靠。

### Anchor

```ts
type TextAnchor = {
  passageId: string;
  start: number;
  end: number;
  exact: string;
  prefix: string;
  suffix: string;
};
```

所有 AI 注释、专名线、个人批注都使用这一套 anchor。

不要只存 `{start, end}`。

# 4. 原文范围

## 4.1 主阅读 corpus：完整《通鉴纪事本末》

V0.1 importer 目标：

- 从维基文库主目录发现卷链接。
- 校验应有卷数 = 42。
- 抓取正文。
- 生成 catalog / volumes / passages。
- 保留 source page + revision metadata。
- importer 如果发现卷数不对、空页、页面异常：**fail loudly**，不要静默生成“看起来完整”的书。

### 完整性测试

必须存在自动测试：

```text
expected_volume_count == 42
actual_volume_count == 42
every volume has >= 1 passage
no passage text is empty
```

---

## 4.2 古注 fixture：胡三省注《资治通鉴》

V0.1 **不要求**解决全部胡注页面的通用 parser。

只要求：

- 选一卷 / 一个经过人工确认的 section 作为 fixture。
- 数据模型能区分 `canonical_text` 与 `source_note`。
- UI 能正确显示夹注或段后注。
- 古注可再被专名线/AI 第一二层注释处理。

只要这一条跑通，说明架构没有堵死；通用胡注 importer 留给 V0.2。

# 6. AI 第一/第二层注释

## 6.1 古文 LLM 固定使用科大 DeepSeek V4.1 Flash

Coding 模型绝不替代它。

Python 读取：

```bash
GUJI_LLM_BASE_URL
GUJI_LLM_API_KEY
GUJI_LLM_MODEL
```

`.env` 不进入 git。

`.env.example` 只写变量名。

---

## 6.2 Generator 单次输出

同一 passage 一次生成：

1. 专名 spans
2. 第一层人物 / 地名 / 难词注释
3. 第二层官职职能 / 非传主人物首次重要出场

要求严格 structured JSON。

### 第一层

`PERSON`
- 识别字、号、官职、爵位、籍贯等代称。
- 尽量 resolve 到同一人物。
- 只写阅读本段所需信息。
- 30–80 字为主。

`PLACE`
- 古地名。
- 给现代大致位置。
- 不确定必须写“约 / 大致 / 今某地一带”，不得伪造精确坐标。

`TERM`
- 高中文化一般水平可能难懂的文言词/古今异义/特殊语法/制度词。
- 不给显然词语强行加注。

### 第二层

`OFFICE`
- 必须绑定本段时代。
- 解释当时的大致职能，不允许拿后朝制度硬套。

`FIRST_APPEARANCE`
- 当前 reading unit 内“非主角重要人物”的首次重要出场。
- V0.1 对《通鉴纪事本末》以当前事件/篇目为 reading unit。

---

## 6.3 Reviewer 必须是第二个独立 Flash 请求

Reviewer 输入：

```text
canonical passage
candidate JSON
schema/rubric
```

Reviewer **不接收 generator reasoning**。

输出：

```json
{
  "passage_id": "...",
  "overall": "accept | revise | reject",
  "scores": {
    "proper_name_precision": 1-5,
    "proper_name_recall": 1-5,
    "entity_resolution": 1-5,
    "place_accuracy": 1-5,
    "term_necessity": 1-5,
    "office_accuracy": 1-5,
    "first_appearance_accuracy": 1-5,
    "verbosity_control": 1-5,
    "unsupported_claim_risk": 1-5
  },
  "issues": [...],
  "revised_annotations": [...]
}
```

发布规则：

- `accept`：使用 generator 输出。
- `revise`：使用 reviewer 的 revised_annotations。
- `reject`：该 passage 不显示 AI 注释，并保留报告。

**不得为了“全覆盖”而发布低质量注释。**

- 原文选段
- 用户批注
- 编辑
- 删除

# 8. 不做任意 overlap

为了 V0.1 可靠：

- 如果新 selection 与已有 user annotation 范围重叠，先阻止创建并提示。
- AI annotation 与 user annotation 可以视觉叠加，因为 AI 层不修改 DOM canonical text；实现时使用统一的 range segmentation renderer。
- 用户对同一 exact range 可以“编辑原标记”，不重复叠多层。

V0.2 再处理任意 overlap interval composition。

# 14. Sticky project rules

`.omp/RULES.md`

```markdown
# Guji Reader V0.1 Rules

1. This is a small local-first reading tool, not a general Reading OS.
2. Do not add features outside docs/V0.1_PLAN.md unless the human explicitly changes scope.
3. Canonical source text is immutable to AI. AI may only create separate annotations.
4. Source notes, AI notes, and user notes must remain distinguishable in data and UI.
5. Never commit API keys, tokens, cookies, or .env.
6. V0.1 has no FastAPI server, no database server, no vector database, no auth, no cloud sync.
7. Prefer simple data files and deterministic transforms.
8. User text selection is limited to one passage in V0.1.
9. Do not silently “fix” source text. Report suspected source errors separately.
10. Importers fail loudly on incomplete or structurally unexpected source data.
11. Every non-trivial feature needs at least one test.
12. Do not refactor working code merely for elegance during the sprint.
13. Avoid introducing a dependency when browser/standard-library code is clearly sufficient.
14. Keep Chinese UI labels concise.
15. Before declaring V0.1 complete, run the full test suite and the independent reviewer.
```

## P03 — Executor：AI 专名线 + 第一/第二层注释

### 对话提示词

```text
本轮只实现 AI annotation pipeline 与其 UI。

必须遵守：
- 古文生成/复核模型固定使用环境变量指定的科大 DeepSeek V4.1 Flash。
- coding 模型不得伪造任何 annotation 数据。
- canonical text 不可修改。

实现：

1. scripts/check_llm.py
   - 检查环境变量
   - 做一个极小 JSON structured-output canary
   - 不打印 API key

2. scripts/annotate.py
   输入 Passage，输出严格 schema：
   - proper-name spans
   - Layer 1: PERSON / PLACE / TERM
   - Layer 2: OFFICE / FIRST_APPEARANCE
   - confidence
   - TextAnchor

3. scripts/review_annotations.py
   必须发起独立第二次 Flash 请求。
   reviewer 看 canonical passage + candidate JSON + rubric；
   不看 generator reasoning。
   输出 accept/revise/reject + 评分 + issues。

4. publish gate
   - accept -> generator
   - revise -> reviewer revised output
   - reject -> 不发布
   - 所有原始和 review 结果留在 data/

5. 给脚本支持：
   - --passage
   - --volume
   - --limit
   不要求本轮把 42 卷全部跑完。

6. 用少量人工可核验 passage 生成真实 annotation fixture。

7. 前端：
   - 专名线开关
   - 横排/竖排都正确
   - “注”小标
   - 点击 popover
   - 点击外部关闭
   - source 古注与 AI 注释外观必须不同
   - PERSON / PLACE / TERM / OFFICE / FIRST_APPEARANCE 显示简洁标签

8. 写测试：
   - schema invalid 必须 fail
   - rejected annotation 不发布
   - exact anchor 与 text 不一致必须 fail
   - proper-name renderer
   - popover
9. Playwright smoke-2 通过。
10. 生成：
   data/review_reports/v0.1_annotation_quality_summary.json

最后报告：
- 跑了多少 passages
- accept/revise/reject 各多少
- 每类平均评分
- 发现的主要问题

不要做第三层总结。
不要做现代论文搜索。
```

### 人工验收

如果问题明显，改 prompt/schema，再跑 fixture；不要先全书批处理。

# 17. 你自己的最终人工验收

模型全部说 PASS 后，你还要自己做 10–15 分钟真实使用：

1. 随机开《通鉴纪事本末》一卷。
2. 横排读几段。
3. 竖排读几段。
4. 点 10 个 AI 注。
5. 高亮 2 处。
6. 波浪线 2 处。
7. 写 2 条批注。
8. reload。
9. 关闭浏览器再打开。
10. 确认标记仍在。
11. 找一处你觉得 AI 解释不对的地方，确认“关 AI 后原文仍然完全干净”。

最后只问自己：

> “我今晚会不会真的愿意用这个读 30 分钟？”

如果答案是“会”，V0.1 就完成了。

如果答案是“不会”，只修阻碍阅读的地方，不扩功能。
